# سياسات الحجز والتأكيد والتعارض

> التاريخ: 2026-10-31 · تُطبَّق من الخادم فقط (RPC + API)، الواجهة تعرض ولا تقرر.

## 1. مدة تعليق التواريخ (Pending Hold)

- عند طلب حجز (من صفحة الحجز المباشر) تُحجز التواريخ فورًا بحالة `pending` **لتمنع أي حجز متنافس** أثناء انتظار التأكيد.
- المدة قابلة للضبط لكل منظمة: `organizations.settings.hold_hours` — **الافتراضي 24 ساعة** (حدود مسموحة: 1–72).
- job دوري (`booking.expire`) يمرر أي `pending` تجاوزت `expires_at` إلى `expired` فيحرر التواريخ تلقائيًا.
- التأكيد اليدوي من لوحة التحكم يلغي الساعة (status → `confirmed`).

## 2. آلة الحالات

```
pending  → confirmed | cancelled | declined | expired
confirmed → checked_in | cancelled
checked_in → checked_out
(كل الحالات النهائية: checked_out/cancelled/declined/expired لا تتغير)
```
- انتقال غير قانوني → 422.
- الحالات الحاجزة للتواريخ: `pending`, `confirmed`, `checked_in` + كل `kind='block'` (iCal).

## 3. منع التعارض

- قيد Postgres EXCLUDE (انظر ADR 0002) — التحقق النهائي دائمًا في قاعدة البيانات، لا في التطبيق.
- الليالي `[check_in, check_out)`: المغادرة صباحًا تسمح بوصول نفس اليوم.
- أي كاتب (لوحة/صفحة عامة/iCal/API) يخضع لنفس القيد؛ خطأ التعارض → 409 "التواريخ محجوزة".

## 4. الدفع (حتى تفعيل Moyasar/HyperPay)

- طلب الحجز المباشر **لا يتضمن دفعًا** — يصل المالك كما طلب حجز (pending) ببيانات الضيف.
- عند توفر مفاتيح الدفع (P1): رابط دفع بمدة صلاحية = مدة التعليق، نجاح الدفع → تأكيد تلقائي (`paid_at` + webhook idempotent)، فشل/انقضاء → إعادة التحرير.
- الحجوزات اليدوية (من اللوحة) تبقى بدون دفع إلزامي.

## 5. الكتل الخارجية (iCal)

- كتلة مستوردة = حقيقة خارجية: لا تُعدَّل ولا تُلغى من عندنا؛ تُحدَّث/تزول مع المزامنة التالية للمنصة المصدر.
- تعارض كتلة مستوردة مع حجز داخلي قائم → تسجيل `sync_issue` + تنبيه المالك في اللوحة (لا تعديل تلقائي لأي طرف).

## 6. الصلاحيات

- إنشاء/تعديل/إلغاء حجز: `org_owner`, `org_admin`, `manager`.
- انتقالات الحالة (وصول/مغادرة): يشملهم + `staff`.
- الضيف يرى صفحة وحدته العامة فقط.
